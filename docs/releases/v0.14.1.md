# Fulcrum Boundary v0.14.1

> **Release-stamp candidate — not published.** Neither `v0.14.1` nor
> `verify-witnessed/v0.14.1` exists yet. Every install command on this page is
> future, post-publication material and must not be used until both tags are
> explicitly approved, point to the same exact commit, and publish successfully.
> The published release remains `v0.14.0`. Publication facts are recorded in
> `docs/RELEASE_TRUTH_PUBLIC.md` after publication, not here.

`v0.14.1` is a patch release for one verified defect in the offline
witnessed-log verifier (`verify-witnessed`). It changes no enforcement
behavior, adds no feature, and upgrades no claim.

Scope: Boundary decides before execution only for actions forced through a
governed Boundary route. This release concerns only the offline verification of
the decision records those routed decisions produce. MCP remains the only
production adapter; Command Boundary, Edit Boundary, Secure GitHub, CLI,
CodeExec, gRPC, Managed Agents, Webhook, and A2A remain preview. Decision
records remain hash-verifiable for covered-field integrity only — not
authenticity, signing, verdict correctness, enforcement, or completeness — and
Boundary does not emit `proved` decisions.

## Known issue in v0.14.0

The nested `verify-witnessed` module published at `v0.14.0` rejects a
witnessed-bundle decision record that carries any of these members:

- `request_id` — the request correlation id that `BuildDecisionRecord` copies
  into a record when the pipeline assigned one, and that
  `check_indeterminate` records carry as required context.
- `check` (`stage`, `class`, `category`, `cause`) — the ADR-047
  `check_indeterminate` context.
- the schema_version "2" route-context members `adapter_id`, `route_id`,
  `topology_profile`, and `execution_claim` (`upstream_called`, `executed`,
  `source`).

The verifier's record type did not define those members, and its strict
decoder rejects every member it does not define, so the record failed to decode
and the bundle's `decision_record_integrity` check failed. A decode failure
also fails `manifest:decisions.jsonl`, because the manifest check needs every
decision line to decode (`decisionManifestOK` in `verify.go`), so one such record
fails two checks.

This is not a corner case. The production MCP adapter
(`adapters/mcp/adapter.go`) sets `RequestID` (a UUID) on every request it
governs, and `BuildDecisionRecord` copies it into the record. Every decision
record from the production MCP route at `v0.14.0` therefore carries
`request_id`, and `verify-witnessed` at `v0.14.0` fails effectively every real
witnessed bundle that holds such a record, even though each record's
`decision_hash` is correct. The failure is a false rejection, not a tamper
finding.

What is not affected:

- `boundary verify-record` and the Go, Python, TypeScript, and Rust record
  verifiers already accept these members; the conformance vectors
  `v1_request_id`, `v1_check_indeterminate`, and `v2_route_context` verify
  there.
- Enforcement. Which routed calls Boundary allows, holds, or denies is
  unchanged, and so is the content of every record.
- The witnessed-log checks other than `decision_record_integrity` (manifest,
  inclusion proof, tree head signature, cosignatures) were not changed.

Workaround until `v0.14.1` publishes: build `verify-witnessed` from a source
checkout that contains this fix, or verify each record with
`boundary verify-record`. That command takes one JSON object per file, so
extract each line of the bundle's `decisions.jsonl` first:

```bash
n=0
while IFS= read -r line; do
  n=$((n+1)); printf '%s\n' "$line" > "record-$n.json"
  boundary verify-record "record-$n.json"
done < decisions.jsonl
```

`verify-record` checks only each record's own `decision_hash`; it does not
check the inclusion proof, the signed tree head, the cosignatures, or the
manifest, which are the other checks `verify-witnessed` performs.

## What changed

- **implemented** — `verify-witnessed`'s record type now mirrors
  `governance.DecisionRecordV1` exactly: the same JSON member names and
  `omitempty` behavior, including `request_id`, `check`, `adapter_id`,
  `route_id`, `topology_profile`, and `execution_claim`, with the nested
  `check` and `execution_claim` objects. `decision_hash` is recomputed over all
  members with the same RFC 8785 canonicalization as
  `governance.ComputeDecisionHash`. `schema_version` `"1"` and `"2"` are
  accepted.
- **implemented** — The verifier's record decoder applies the same member-level
  ingest rules as `governance.DecodeDecisionRecord`: case-folded
  duplicate-member rejection at every depth, closed exact-case member sets for
  the record, `check`, and `execution_claim`, and trailing-data rejection. The
  verifier is stricter than that decoder on inputs Boundary never emits; see
  below. The CLI reports pass or fail per check. The rejection classes
  (`duplicate-key`, `unknown-field`, `trailing-data`, `not-object`,
  `parse-error`) are used by the tests, which classify each rejected corpus
  vector against the corpus vocabulary; `validate()`-stage rejections
  (unsupported `schema_version`, missing or empty required members, malformed
  hashes, bad decision mode, bad timestamp, signature pairing) classify as
  `parse-error` in the verifier, where `governance.VerifyDecisionRecord`
  reports `schema-version` and `hash-mismatch`. The corpus has no vector for
  those classes.
- **tested** — `verify-witnessed` now pins a byte-for-byte copy of the
  decision-record conformance corpus and runs every vector against its
  manifest verdict: `verify` vectors decode and recompute to the stored
  `decision_hash`; `reject:hash-mismatch` vectors decode and recompute to a
  different hash; every other `reject:<class>` vector fails decode with that
  class.
- **tested** — The corpus gains vectors for every `decision_mode` value
  (`v1_mode_classified`, `v1_mode_proved`, `v1_mode_human_approved`; the
  `deterministic` mode was already covered), a signed record
  (`v1_signed_record`), and a record carrying every optional member at once
  (`v2_all_members`), so signature and key-id blanking in the `decision_hash`
  recomputation is exercised. The signature bytes are fixture values, not valid
  signatures; these vectors pin hash coverage, not signature verification, and
  are integrity-only fixtures, not a claim that Boundary emits such decisions.
- **tested** — Root-module tests fail when the pinned corpus differs from
  `tests/conformance/testdata/verifier-vectors`, when the verifier's record
  type differs from `governance.DecisionRecordV1` in member set, `omitempty`
  flags, or nested objects, or when the verifier's accepted `decision_mode`
  values or `schema_version` values differ from the `governance` constants. A
  record field, mode, or schema version added in `governance` without a
  verifier update now turns CI red.
- **tested** — `TestWitnessedBundleWithEveryRecordMember` assembles a complete
  witnessed bundle (decisions, declines, inclusion proof, signed tree head, two
  cosignatures, manifest) around corpus records that carry `request_id`, `check`,
  schema_version "2" route context, and signature members, and requires all 12
  checks to pass. It fails against the `v0.14.0` verifier code.

### Where the verifier is stricter than Boundary

`verify-witnessed` rejects some inputs that `governance.DecodeDecisionRecord`
and `boundary verify-record` accept. Boundary never emits any of them, so no
record it produces is affected:

- a JSON `null` on any member that is present;
- a missing `check.stage`, `check.class`, or `check.category`, or a missing
  `execution_claim.upstream_called` or `execution_claim.executed`;
- invalid UTF-8 and lone UTF-16 surrogate escapes;
- a timestamp that is not canonical UTC RFC 3339 (`+00:00`, `+01:00`, or a
  fractional part with trailing zeros such as `.120Z`);
- a missing `schema_version`, `record_id`, `timestamp`, `action`, `decision_hash`
  or `trust_score`, or an empty `record_id` or `action`;
- a `decision_mode` outside `deterministic`, `classified`, `proved`, and
  `human_approved`;
- a malformed `policy_bundle_hash`, `request_hash`, or `raw_shape_hash`;
- a `signature` without a `signature_key_id`, or the reverse, or a malformed
  signature or key id.

Most of these rules predate this release (they come from the verifier's
`validate()` and strict JSON layers) and are unchanged by it.

## Install

These commands become valid only after both `v0.14.1` tags publish; the
published release remains `v0.14.0` until then.

```bash
brew install fulcrum-governance/tap/boundary
docker pull ghcr.io/fulcrum-governance/boundary:v0.14.1
go install github.com/fulcrum-governance/fulcrum-boundary/cmd/boundary@v0.14.1
```

Install the nested verifier from its source-distribution tag once published:

```bash
go install github.com/Fulcrum-Governance/Fulcrum-Boundary/verify-witnessed@v0.14.1
```

The verifier does not have its own prebuilt archive, container, Homebrew
package, or version flag.

## Compatibility

- No behavior change for the `boundary` CLI, the adapters, policy loading, or
  the content of decision records.
- `verify-witnessed` now accepts well-formed records it previously rejected.
  It also applies the case rules the other record verifiers apply: a member
  name that differs from a schema member only in case is rejected as an
  unknown field, and two members that differ only in case are rejected as
  duplicates. The `v0.14.0` verifier bound such names case-insensitively, so a
  record that relied on that is newly rejected; no well-formed record that
  `v0.14.0` accepted is.
- This is a pre-1.0 release. See `CHANGELOG.md` for the `v0.14.0..v0.14.1`
  delta.
- No claim upgrades on publication alone; tagged-publication evidence is
  recorded separately in `docs/RELEASE_TRUTH_PUBLIC.md`.
